# 渲染通道:哪种写法在哪里出图

## 实测矩阵

| 客户端 | Mermaid | 内联 SVG | 图片引用 | 嵌套列表 |
|---|---|---|---|---|
| Claude Code 终端 | ✗ 源码 | ✗ 源码 | ✗ | ✓ |
| Claude Desktop · Claude Code 标签页 | ✗ 源码 | ✗ 源码 | — | ✓ |
| Claude Artifact 页面 | ✓ | ✓ | — | ✓ |
| 某 Markdown 渲染视图(客户端待确认) | ✓ | ✗ 源码 | ⚠ 待重测 | ✓ |
| Codex CLI 终端 | — | — | — | — |
| VS Code Markdown 预览 | (✓) | (需扩展) | (✓) | ✓ |
| GitHub 仓库页 | (✓) | (被过滤) | (✓) | ✓ |

`✓` 出图 · `✗` 不出图 · `—` 未测 · `⚠` 测过但结果不可信 · `(括号)` 依据文档预期,未实测。

**可信的结论:**

- **只有嵌套列表这一列在所有测过的行里全绿。** 这就是存储格式必须用它的全部理由——不是审美,是交集。
- **mermaid 在两个终端类客户端确定显示为源码**,有 [claude-code#52517](https://github.com/anthropics/claude-code/issues/52517) 佐证,而这两处正是这份文件最常被读到的地方。
- **`.svg` 文件单独打开能正常渲染**(截图有完整路径面包屑佐证),所以 SVG 作为"独立文件直接打开"的展示方式可用。

**存疑的两处,不要当结论用:**

- 第四行的客户端名称未被确认,是从"当时在讨论 Codex 兼容性"推断的。测量记录里不能放推断。
- 图片引用那一列的失败可能是测试环境造成的:如果当时打开的是脱离了同目录图片的 `probe.md` 副本,相对路径解析失败与客户端能力无关。`render-probe/probe.md` 已把这一列拆成五个变体(同级相对、`./` 前缀、绝对路径、PNG 对照、远程 URL)来隔离病因。

这两处存疑**不影响存储格式的结论**——嵌套列表全绿是独立成立的。受影响的只是"展示层能不能用图片引用"这个次要问题。

## 存储层与展示层分开

这是整件事的关键,混在一起就会得出"要为某个客户端选一种格式"的错误结论。

**存储层**是 `dialog-map.md` 本身。它会被下一个会话的 agent 当文本读,也会被你在终端、编辑器、网页里翻看。它必须取所有客户端的**交集** = 嵌套列表。这一层与客户端无关,Codex 读它和 Claude 读它一样好。

**展示层**是"人想看一张放射状的图"时的临时产物。它取客户端的**并集**,现场生成、看完即弃。

## 想看图时怎么生成

按覆盖面从宽到窄:

1. **Mermaid mindmap** —— 默认选这个,覆盖面最广。Claude Artifact 已实测出图,GitHub、Obsidian、VS Code 按文档支持,另有一个 Markdown 渲染视图实测出图。直接把列表转成 `mindmap` 语法贴给用户,或写进要提交的 README。
2. **Artifact 页面** —— 需要一个能反复回看、能分享的入口时用。mermaid 和 SVG 在里面都渲染,可以做得比 mermaid 默认布局好看很多。
3. **独立 `.svg` 文件** —— 需要一张能拖进别处的图片时用。写成单独文件让用户直接打开(这一条已实测可行);**不要**内联进 Markdown——内联在终端类客户端和上面第四行都确定失败。用 `![](x.svg)` 引用是否可行还没测清,想用先跑 `render-probe` 的 B2 系列。

## Mermaid mindmap 的语法坑

生成 mermaid 时会踩到,写之前先看:

**括号、冒号、方括号导致解析失败。** 节点文本里出现 `(` `)` `[` `]` `{` `}` `:` 时,mermaid 会当成形状语法然后报错:

```
✗ 双层结构(图+决策)        <- 渲染失败
✓ 双层结构 图加决策         <- 改写,推荐
✓ ["双层结构(图+决策)"]     <- 引号包裹,能用但啰嗦
```

**层级完全由缩进决定**,同级缩进必须严格一致,否则整块失败。根节点 `root((文字))` 圆形、`root[文字]` 方形;子节点直接写文字。

**不支持跨分支连线。** 需要表达"A 支的结论影响 B 支"时,在节点文本里带上决策编号让读者跳转;真需要图关系就换 `flowchart`,不要硬掰 mindmap。

**单节点着色不可靠。** class 和 icon 支持在各渲染器间不一致,所以状态继续用文本前缀符号(`✓ ✗ ? !`),不要靠颜色。

## 绝不要同时存两份

不要在 `dialog-map.md` 里既维护嵌套列表又维护一段 mermaid。两份结构手工同步必然漂移,漂移之后你不知道该信哪一份,文件就废了。列表是唯一事实来源,mermaid 每次从它现场生成。

## 换了客户端怎么重测

上面的矩阵会过期——客户端一直在加渲染能力。重测方法:写一个文件,把同一棵小树写成 mermaid 代码块、内联 SVG、`![](x.svg)` 引用、嵌套列表四种形式,每种下面注明"通过长什么样",然后在目标客户端里打开。本仓库的 `render-probe/probe.md` 就是一份现成的,直接用。

关键是**看列不看行**:哪一列在你实际会用到的客户端里全绿,那一列就是存储格式;覆盖面最广的列作为默认展示格式,而不是最好看的那一列。
