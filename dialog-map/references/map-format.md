# 脑图格式与增量更新

## 为什么是嵌套列表,不是 Mermaid

脑图部分用嵌套 Markdown 列表。这不是审美选择,是实测出来的——见 [rendering.md](rendering.md) 的渲染矩阵:四种环境里**只有嵌套列表全部出图**。mermaid 在 Claude Code 终端和 Claude Desktop 的 Claude Code 标签页显示成源码,而这两处正是这份文件最常被读到的地方;内联 SVG 更窄,连支持 mermaid 的 Markdown 渲染视图都把它当源码。嵌套列表在任何环境下都能读:终端里是缩进纯文本,Markdown 渲染器里是折叠列表。

存储格式取所有客户端的**交集**,展示格式才取并集——这是两个不同的问题,混在一起就会得出"要为某个客户端选一种格式"的错误结论。

而且这份文件的**第一读者其实是下一个会话的 agent**,它是当文本读的——对它来说 mermaid 只是更难解析的等价物,一点好处都没有。

## 格式

```markdown
- **skills 仓库**
  - steelman skill
    - ✓ 两轮流程 第一轮止于唯一问题 · D1
    - ✗ 一次性给出判断 · D1
  - dialog-map skill
    - ✓ 双层结构 脑图加决策记录 · D5
    - ✗ 只做脑图 · D5
    - ? PreCompact 接法未实测 · Q2
    - ! 终端与桌面端都不渲染 mermaid
```

- **根**:项目名,加粗。不是本次讨论的主题——文件是项目级的,跨会话累积。
- **一级**:议题。一个议题对应一个能独立结束的问题,结束后整支可归档。
- **二三级**:该议题下的结论、否决项、待决问题、约束。深度控制在三层内,再深说明议题该拆了。
- **状态标记**放在文本最前,**编号**用 ` · ` 接在末尾指向决策记录或待决问题。
- **节点文本一行以内**。写长了说明内容属于决策记录,不属于图。

| 标记 | 含义 | 用在哪 |
|---|---|---|
| `✓` | 已定 | 已经做出的选择 |
| `✗` | 已否决 | 考虑过并放弃的路径,保留不删 |
| `?` | 待决 | 悬而未决,对应一个 Q 编号 |
| `!` | 约束 | 撞到的客观事实,如某 API 需认证、某目录只读 |

嵌套列表没有 mermaid 那些语法陷阱,括号冒号方括号都可以直接写。唯一要求是缩进保持一致(每级两个空格)。

## 增量更新时挂到哪

新内容按这个顺序找位置:

1. **能挂到已有议题下** → 挂进去,不新建一级分支。
2. **是对已有节点的推翻** → 把原节点标记改成 `✗`,在它下面新增 `✓` 节点,两者指向同一个决策编号(决策记录里写清推翻的理由)。
3. **确实是新议题** → 新建一级分支。

第 2 种最容易被做错成"直接改写原节点"。改写会让图一直很干净,但丢掉了"我们试过那条路",下个会话就会再试一次——而这正是这份文件存在的主要理由。

## 单一事实来源

只维护这份列表。需要放射状图像时从列表现场生成(见 [rendering.md](rendering.md)),不要在文件里同时存一份 mermaid——两份结构手工同步必然漂移,漂移之后你不知道该信哪份,文件就废了。
