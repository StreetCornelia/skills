# 对话脑图(dialog-map)

对话里最先消失、又最难重建的不是代码,是**判断**:为什么走这条路、否决了什么、当时依据的约束是什么。代码在 git 里,文件在磁盘上,只有这些判断随上下文窗口一起蒸发,于是下一个会话(或下周的你)会重新踩一遍同样的坑,或者把已经否决的方案当新想法重提。

本 skill 维护一份 `dialog-map.md` 来接住这部分。它是**增量**的:每次触发只追加自上次水位以来的新内容,不重写全文——重写会抹掉思考的演进轨迹,而轨迹本身就是价值。

## 为什么是两层

只有脑图不够。脑图擅长表达结构(问题分几支、每支下有什么),但节点里塞不进"因为 X 所以选 A"这种带推理链的内容,更装不下被否决的路径。只有线性记录也不够:翻到第 40 条时你已经不知道它属于哪个议题。

所以:**脑图是索引,决策记录是正文**。脑图节点用编号(D1、D2)指向决策记录,读的时候先看图定位,再跳到对应条目看理由。

## 触发时的执行流程

### 1. 读取现状,确定水位

先读项目里的 `.claude/dialog-map.md`(不存在则用 [assets/dialog-map-template.md](assets/dialog-map-template.md) 建立)。文件顶部的**更新水位**记录了上次覆盖到哪里。只处理水位之后的对话,已入图的内容不重复处理——这是保证多次触发不产生重复节点的关键。

首次建立时,把整段对话都当作水位之后的内容处理。

### 2. 筛选值得入图的内容

这一步决定了文件是资产还是垃圾。判断标准只有一条:**它会随上下文消失,且未来会被再次需要吗?**

值得记的:

- **决策**:在多个选项里选定了一个
- **否决**:考虑过但放弃的路径,以及放弃的理由(价值最高,最容易被后人重提)
- **约束发现**:过程中撞到的事实(某 API 不支持、某目录只读、某工具需要认证)
- **待决问题**:悬而未决、且会阻塞后续的问题

不要记的:

- 执行动作的流水(改了哪个文件、跑了哪条命令)——git 和磁盘已经记了
- 对话的礼节性往返、澄清性问答
- 可以从代码当前状态一眼看出的结论

一轮对话可能什么都不值得记,那就不记,只推进水位。宁可空,不要灌水:文件一旦变成逐句记录,下次就没人读了,skill 也就废了。

### 3. 更新脑图

把新内容挂到已有节点下,而不是新建平行分支——除非确实开了新议题。节点文本前加状态标记,让"思考过程"可见:

- `✓` 已定 · `✗` 已否决 · `?` 待决 · `!` 已发现的约束

被否决的节点**保留在图里**,不要删。删掉它,图就只剩结论,失去了"这条路试过了"的信息,而这正是最容易被重复浪费的部分。

**脑图用嵌套 Markdown 列表写,不要用 Mermaid、也不要用 SVG。** 这是实测结论:在 Claude Code 终端、Claude Desktop 的 Claude Code 标签页、Claude Artifact、Codex 桌面应用四个客户端里逐一验证,**只有嵌套列表处处出图**;mermaid 在两个终端类客户端显示成源码,SVG 嵌进 Markdown 后在 Codex 桌面被当源码或降级成链接。完整矩阵见 [references/rendering.md](references/rendering.md)。

理由不是审美而是交集:这份文件会被多个客户端反复读到,第一读者还是下一个会话的 agent——它当纯文本读,mermaid 对它只是更难解析的等价物。

人想看放射状图像时**现场生成、看完即弃**,默认用 mermaid(覆盖面最广的展示格式),需要可分享入口时发布成 Artifact,需要一张可拖走的图片时写成独立 `.svg` 文件。生成方法和 mermaid 的语法坑都在 [rendering.md](references/rendering.md) 里。绝不要在文件里同时长期维护列表和 mermaid 两份结构——手工同步必然漂移,漂移之后你不知道该信哪一份。

格式细节与增量更新时的挂载判断见 [references/map-format.md](references/map-format.md)。

### 4. 写决策记录

每条决策用统一结构,其中**失效条件**最容易被略过,但它决定了这条记录是活的还是死的:没有失效条件,未来的你不知道什么时候该重新审视它,只能盲从或全盘推翻。

```markdown
### D<N> · <一句话结论>
- **决定**:选了什么
- **理由**:关键推理链,不超过三句
- **否决了**:哪些备选,各自因为什么被排除
- **失效条件**:什么变化会让这个决定需要重审
```

### 5. 压缩已覆盖的段落

把水位到现在这段对话,在**压缩时间线**里收敛成一到两行,指向已入图的节点或决策编号。这一节的作用是让人快速看清"这个项目走过哪些阶段",细节都在上面两层里。

### 6. 更新水位并汇报

改写顶部的更新水位(时间 + 覆盖到哪个节点),然后向用户简报:新增了哪几个节点/决策、有哪些待决问题。不要复述整个文件。

## 关于"自动触发"和"压缩对话"

两件事需要说清楚,避免预期错位:

**skill 无法自己醒来。** 它是被动的指令文档,没有定时器。要接近"隔一段对话自动触发",得靠 Claude Code 的 hooks 注入提醒,配置方式见 [references/auto-trigger.md](references/auto-trigger.md)。最省心的用法其实是手动:在你感觉"这段讨论有价值"或"上下文快满了"的时候说一句"更新脑图"。

**skill 不能删除上下文。** 真正压缩上下文的是 `/compact` 或自动压缩。本 skill 的作用是让压缩**变得安全**:先把判断落盘到磁盘,再压缩就不怕丢——压缩摘要是尽力而为的,而 `dialog-map.md` 是确定的。所以最有价值的触发时机是 `/compact` **之前**,以及开新会话继续同一主题时**先读它**。

## 文件位置与体量

默认 `.claude/dialog-map.md`(项目内)。要让团队看见就提交进 git,只给自己用就加进 `.gitignore`——两种都合理,取决于这些判断是不是团队资产。

一个项目一个文件,脑图根节点是项目,一级分支是议题。超过约 400 行时,把已完成且不会再改的议题移到文件末尾的**已归档**一节,或拆出 `dialog-map-<议题>.md`。别让文件长到没人愿意读第一屏。
