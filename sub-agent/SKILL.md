# Sub Agent

将主 Agent 作为编排者，把实际任务交给一个或多个子 Agent 完成。主 Agent 负责拆分、调度、协调、验收和汇总，不自行替代子 Agent 完成实质性任务。

## 强制规则

1. 至少启动一个子 Agent。即使任务很小或不可拆分，也必须由一个子 Agent 执行实际工作。
2. 先判断任务是否能够拆成彼此独立或低耦合的工作单元。能够拆分时，默认启动多个子 Agent 并行执行。
3. 优先并行处理互不依赖的调查、实现、测试、审查、资料整理或方案比较；只有存在真实输入依赖时才串行。
4. 不为制造并行而重复分配同一任务。每个子 Agent 必须有清晰、互斥、可验收的职责。
5. 用户明确指定的编排方案优先，包括子 Agent 数量、任务分工、先后顺序、模型、推理强度、交付物和是否允许嵌套委派。
6. 遵守当前环境的并发槽位、工具权限和安全限制。任务数超过可用并发时，分批并行调度。
7. 如果子 Agent 能力不可用或无法启动，立即说明阻塞原因，不得静默改为主 Agent 独立执行。
8. 子 Agent 的最终报告用户看不到。主 Agent 必须在最终答复中转述用户需要的全部结论，不能只说"子 Agent 已完成"。

## 编排流程

### 1. 解析用户约束

提取目标、交付物、完成标准、范围、依赖与用户指定的子 Agent 编排要求。用户没有指定编排时，使用以下默认流程。

### 2. 判断可拆分性

满足任一条件时，视为可拆分：

- 存在两个及以上互不依赖的模块、文件、数据源或研究方向。
- 调查、实现、测试、审查可以由不同子 Agent 独立推进。
- 多个候选方案可以并行分析后再比较。
- 一个主任务包含可独立验收的多个交付物。

只有当任务是单一原子操作、所有步骤存在严格连续依赖，或拆分协调成本明显高于收益时，才使用单个子 Agent。

拆分粒度以"一个子 Agent 一次能独立交付并验收"为准，通常 2–5 个子 Agent 已覆盖大多数任务；不要为了显得并行而切得过碎，碎片化拆分只会增加协调和汇总成本。

### 3. 评估规模并选择模型

派发前对每个子任务做粗略评估，据此决定模型、执行方式和是否再拆：

- **模型选择**：默认继承当前会话的模型。任务机械、指令明确、结果易验收（批量改写、格式转换、按清单核对、简单定位检索）时，可降级到更小更快的模型；需要复杂判断的任务（架构权衡、疑难调试、安全审查、对抗性验证、开放式研究）用当前最强模型。拿不准就继承默认——把判断型任务派给小模型省下的成本，通常抵不上返工。推理强度同理：机械任务用低强度，验证和评审用高强度。用户指定的模型和强度始终优先。
- **预期耗时**：估计子任务大约需要多少轮工具调用。耗时长且互不依赖的任务优先后台并行推进；只有下一步强依赖其结果且期间无其他事可做时才前台等待。单个子任务预计明显超长时，先拆分或分批，不要指望一个子 Agent 一口气跑完。
- **上下文消耗**：子 Agent 拥有独立上下文，这正是委派的核心价值——大量读文件、翻日志、跑测试的重活在子 Agent 内部消化，只把结论带回主对话。为控制主对话的消耗，输出契约应要求"结论 + 必要证据"，禁止整段转储原始文件或日志。单个子任务的阅读/修改范围一个上下文装不下时（如横跨数百个文件的迁移或审计），按分片拆成多个子 Agent，而不是让一个子 Agent 硬扛到上下文耗尽。

### 4. 编写子任务指令

子 Agent 不共享主对话的上下文。每条指令必须自包含，单独拿出来也能执行。指令中必须包含：

- **目标与范围**：要完成什么、做到什么程度算完成。
- **完整上下文**：相关背景、绝对路径、输入数据、已知约束。不要引用"上面提到的""刚才那个文件"这类只有主对话才懂的指代。
- **边界**：不得触碰哪些文件或范围，避免与其他子 Agent 冲突；是否允许修改文件（只读调查任务要明说只读）。
- **输出契约**：要求返回的具体内容和格式，例如"列出每个问题的文件路径、行号和一句话说明"。子 Agent 的最终回复就是交付物，必须要求它返回可直接使用的结果，而不是过程描述。
- **依赖输入**：串行任务中，把上游子 Agent 的实际产出（而非"参考前一步"）写进下游指令。

涉及共享文件写入时，按文件或模块划分所有权。无法隔离写入范围时，二选一：让一个子 Agent 负责全部修改，其他子 Agent 只做只读分析、测试或审查；或使用环境提供的隔离机制（如 git worktree 隔离），让多个子 Agent 在各自副本上工作，由主 Agent 协调合并。

### 5. 并行执行与协调

一次启动所有当前无依赖且并发槽位允许的子任务——在同一轮里同时发出多个子 Agent 调用，而不是逐个启动逐个等待。主 Agent 在子 Agent 工作期间只执行编排职责，包括提供补充上下文、解除阻塞、收集进度和安排下一批任务。

需要串行时，在上游子 Agent 产出可用结果后，再将必要结果传给下游子 Agent。不要让下游依赖未完成或未经确认的假设。

已完成的子 Agent 需要补充或追问时，优先通过继续对话机制（如向已有子 Agent 发消息）延续其上下文，而不是新开一个子 Agent 从零开始。

### 6. 验收与补救

检查每个子 Agent 的结果是否满足范围、证据和验收标准。分情况处理：

- **有缺口**：优先让原负责的子 Agent 补充；需要独立验证时，分配另一个子 Agent 复核。
- **返回空结果或明显跑偏**：先检查指令是否缺上下文或有歧义，修正指令后重派（原子 Agent 或新子 Agent 均可），而不是原样重试。
- **子 Agent 失败或中断**：重派一次；连续失败则向用户说明阻塞，不得由主 Agent 悄悄接手实质性工作。

主 Agent 不得以"补救"名义自行补做实质性内容。

### 7. 汇总交付

主 Agent 可以整合、去重和组织子 Agent 已完成的结果，并向用户给出一个自洽的最终答复。说明关键结论、完成状态、验证结果和仍存在的阻塞；无需逐条暴露内部调度过程，除非用户要求。

## 任务过大时升级为独立会话

子 Agent 适合"能在一个上下文内完成、结果可以压缩汇报回来"的任务。出现以下信号时，新开一个独立会话比子 Agent 更合适：

- 任务本身是一个完整项目：需要多轮与用户来回确认、有自己的迭代节奏、预计持续远超本次对话的范围。
- 结果无法压缩汇报：用户需要看到完整过程和中间产物，经主 Agent 转述会大量失真。
- 任务与当前对话的目标基本无关，只是顺带提出，塞进本对话只会稀释两边的上下文。

升级不是主 Agent 单方面的决定：向用户说明理由，建议新开会话（或使用环境提供的派生独立任务机制），并给出一段自包含的交接说明——目标、已知约束、相关路径、当前进展——让新会话能直接开工。用户坚持在本对话完成时，回退到分片多子 Agent 方案执行，并说明可能的折损。

## 默认角色划分

根据任务选择最小且有效的角色集合，不固定套用：

- **调查 Agent**：定位事实、代码路径、资料或约束。
- **执行 Agent**：实现修改或生成主要交付物。
- **验证 Agent**：运行测试、检查结果或做独立复核。
- **比较 Agent**：分别分析不同候选方案。

如果任务只有一个不可拆分的工作单元，只启动一个执行 Agent；主 Agent 仍只负责协调和最终交付。

有可用的专用子 Agent 类型时优先匹配职责：只读搜索用探索类 Agent，规划用规划类 Agent，其余用通用 Agent。用户指定了 Agent 类型或模型时按用户指定执行。

## 环境映射

本 Skill 与具体工具解耦。执行时把上述规则映射到当前环境的子 Agent 机制：

- **Claude Code**：用 Agent 工具启动子 Agent（`subagent_type` 选择类型；并行时在同一条消息中发出多个调用）。默认后台运行，完成后会收到通知；仅当下一步必须依赖该结果且无其他事可做时才前台等待。需要追问已有子 Agent 时用 SendMessage 按名字继续其对话。多个子 Agent 需要并行改文件时用 `isolation: "worktree"`。
- **其他环境**：使用该环境等价的任务委派 / 子任务机制，遵循同样的自包含指令、输出契约和写入隔离规则。
- 环境完全不提供子 Agent 机制时，触发强制规则第 7 条：说明阻塞，不静默降级。
